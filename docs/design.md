# 设计说明

## 两个模块为什么放在一起

待办记录“接下来要做什么”，收藏记录“看到了什么值得留下”。两者的共同点是都发生在浏览器里，都要求“想到就能记，不打断手上的事”。放在一个扩展里，共用一套存储和一个入口，并且能互相转：一段收藏可以变成待办，周回顾里同时看到这周存了什么、做完了什么。

## 取舍

**一句话输入，而不是表单。** 记待办最大的阻力是填表。这里把日期、优先级、项目、重复全部从一句话里读出来，并在输入时实时显示读成了什么。读错的代价只是改这句话。

**解析用规则，不用模型。** 日期和重复写法是有限的，规则可以穷举并逐条测试，结果确定、离线可用、没有费用。代价是不认识规则之外的说法，这时整句话原样成为标题，不会猜一个日期出来。

**收藏之后才问标签。** 先存下来，再在角落里给一个可以忽略的小卡片。不加标签也能存，回顾时会归到“未分类”。

**回顾是整理，不是总结。** 周回顾和月回顾只做确定的事：计数、按标签分组、按天画条形图、找出在多条收藏里重复出现的词。不生成“本周你关注了……”这类概括，因为那需要模型，而且容易说错。

**每日重温用固定间隔。** 间隔是 1、3、7、14、30、90 天。每天默认只拿出 5 条，等得最久的先出。这比按遗忘曲线拟合的算法粗，但不需要用户给记忆打分，三个按钮就够。

**数据只在本机。** 没有服务器就没有账号、同步和泄露问题。代价是换设备要手动导出导入。导入按编号合并，重复导入不会产生重复数据。

## 存储

`chrome.storage.local` 下三个键：待办、收藏、设置。分开存，是为了保存一条收藏时不重写全部待办。

所有写入都是“先读最新值、改、写回”，并在同一个页面里排队执行，连续点两下不会互相覆盖。网页里的内容脚本不直接碰存储，只给后台发消息，所以网页的脚本环境里没有数据，也没有存储代码。

同一套存储代码有三种后端：扩展里用 `chrome.storage`，普通网页里用 `localStorage`，测试里用内存。逻辑层因此可以不启动浏览器就测试。

## 把收藏过的句子再找回来

保存时除了正文，还记下它前后各 40 个字符。再次打开页面时：

1. 把页面所有文本节点连成一个字符串，去掉全部空白；
2. 在里面找去掉空白后的正文；
3. 如果出现多次，用前后文挑出原来那一处；
4. 把字符位置映射回文本节点，逐个节点包上标记。

去掉空白再比较，是因为选区文本和页面源码里的换行、缩进经常不一致。跨越加粗、链接等行内元素的句子会被分成几段标记。

聊天页面和单页应用的内容是后加载的，所以内容脚本会在页面变化后重试，直到找到或者重试次数用完，并在地址变化时重新加载该页的收藏。

## 测试

- `tests/*.test.js`：逻辑层的单元测试，覆盖中英文日期、快速添加、重复规则、任务视图、收藏、重温调度、回顾、文本定位、存储和备份。
- `tests/e2e/run.py`：在真实 Chrome 里加载扩展，在测试页面上收藏、刷新、改标签、转待办，再操作弹窗和完整页面的每一个栏目。
- `tools/check.js`：清单里引用的文件都存在，脚本都能解析，页面引用的文件都存在。
